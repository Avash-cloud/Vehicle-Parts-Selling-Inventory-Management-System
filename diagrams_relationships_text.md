# Diagram Relationships and Flow Descriptions (Plain Text)

Here are the detailed descriptions of the relationships, associations, and flows for each diagram so you can include them in your documentation without any Mermaid code.

---

## 1. ER Diagram Relationships

In the database schema, the entities are connected using primary key and foreign key constraints. Here are the proper textual relationships:

1.  **Customer to Vehicle (1-to-Many):** One Customer can own multiple Vehicles, but each Vehicle belongs to exactly one Customer.
2.  **Customer to Appointment (1-to-Many):** One Customer can book multiple Appointments, but each Appointment is booked by only one Customer.
3.  **Customer to Sales Invoice (1-to-Many):** One Customer can have multiple Sales Invoices, but each Invoice is billed to exactly one Customer.
4.  **Customer to Review (1-to-Many):** One Customer can write multiple Reviews, but each Review is written by one Customer.
5.  **Staff to Sales Invoice (1-to-Many):** One Staff member can generate multiple Sales Invoices, but each Invoice is generated by one Staff member.
6.  **Staff to Purchase Invoice (1-to-Many):** One Staff member can create multiple Purchase Invoices for suppliers.
7.  **Vendor to Inventory (1-to-Many):** One Vendor can supply multiple Vehicle Parts (Inventory items), but each part comes from one specific Vendor.
8.  **Vendor to Purchase Invoice (1-to-Many):** One Vendor can receive multiple Purchase Invoices from the system.
9.  **Inventory to Review (1-to-Many):** One Vehicle Part in Inventory can receive multiple Reviews from different Customers.

## 2. Use Case Diagram Relationships (Associations)

The actors interact with the system functionalities (use cases) through direct associations:

*   **Admin Associations:** The Admin has direct access to *Staff Management, Report Generation, Vendor Management, Inventory Management, Invoice Generation,* and *Customer Search*.
*   **Staff Associations:** The Staff has direct access to *Vendor Management, Inventory Management, Invoice Generation, Customer Search,* and *Parts Selling*.
*   **Customer Associations:** The Customer has direct access to *Customer Registration, Parts Selling* (making a purchase), *Appointment Booking,* and *Review Submission*.

---

## 3. Class Diagram Relationships

The object-oriented structure utilizes associations and dependencies among classes:

1.  **Association (Customer - Vehicle):** A direct association exists where a `Customer` object maintains a list of `Vehicle` objects.
2.  **Association (Customer - Invoice):** A `Customer` object is associated with multiple `Invoice` objects for their purchases.
3.  **Association (Customer - Appointment):** A `Customer` interacts with the `Appointment` class to schedule services.
4.  **Association (Staff - Invoice):** The `Staff` class is responsible for instantiating and managing `Invoice` objects.
5.  **Association (Vendor - Inventory):** The `Vendor` class has an association with the `Inventory` class, representing the supply chain.
6.  **Association (Vehicle - Appointment):** The `Appointment` class relies on the `Vehicle` class to know which car needs servicing.

## 4. Activity Diagram Flow (Process Transitions)

If you need to describe the step-by-step workflow for the Activity Diagram (e.g., the Parts Selling process), here is the text description of the transitions:

1.  **Start to Login:** The process begins when the user accesses the system and attempts to log in.
2.  **Login to Search Parts:** Upon successful authentication, the user transitions to the parts searching interface.
3.  **Search Parts to Add to Cart:** If the desired part is available in the inventory, the user adds it to their cart.
4.  **Search Parts to Update Inventory:** If the part is out of stock, the Staff is prompted to update the inventory.
5.  **Add to Cart to Checkout:** The user proceeds to the checkout interface.
6.  **Checkout to Payment Gateway:** The system verifies the order details and transitions to process the payment.
7.  **Payment Gateway to Generate Invoice:** If the payment is successful, the system automatically generates a sales invoice.
8.  **Generate Invoice to Deduct Inventory:** The stock quantity for the purchased part is automatically deducted from the database.
9.  **Deduct Inventory to Provide Receipt:** The customer is provided with a digital receipt.
10. **End Process:** The workflow terminates successfully.
